> Beauty emerges from understanding. Gates verify the emergence, not the decoration.

## Gate 1: Foundation Gate

### Core Question
**Is this grounded in truth?**

Beauty built on falsehood is illusion that will collapse.

### Gate Criteria

```markdown
## Foundation Gate Checklist

- [ ] Information is accurate
- [ ] Understanding is based on verified facts
- [ ] Confidence is calibrated to evidence
- [ ] Not building on assumptions mistaken for truth

**Foundation Status**: [Solid / Shaky / Crumbling]
```

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Grounded in verified truth | **PASS** |
| Understanding based on accurate info | **PASS** |
| Built on false assumptions | **FAIL** - Fix foundation first |
| Uncertain foundations | **FAIL** - Verify before proceeding |

### When Gate Fails

```
CRITICAL: Cannot proceed to beauty evaluation without solid foundation.

Action:
1. Identify what's uncertain or false
2. Verify or correct the foundation
3. Rebuild understanding on truth
4. Then evaluate beauty
```

---

## Gate 2: Emergence Gate

### Core Question
**Did this solution emerge from understanding, or was it forced onto the problem?**

### Gate Criteria

```markdown
## Emergence Gate Checklist

- [ ] Solution followed from deep understanding
- [ ] Didn't start with solution and fit problem to it
- [ ] Structure reflects actual problem structure
- [ ] Choices feel natural given comprehension
- [ ] Can explain WHY this solution (not just what)

**Emergence Status**: [Emerged / Partially Emerged / Forced]
```

### Emergence Indicators

| Emerged (Beautiful) | Forced (Ugly) |
|--------------------|---------------|
| Problem understood first | Solution assumed first |
| Structure mirrors problem | Structure imposed externally |
| Choices feel inevitable | Choices feel arbitrary |
| Can explain why naturally | Why requires justification |

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Solution emerged from understanding | **PASS** |
| Choices feel natural and inevitable | **PASS** |
| Solution forced onto problem | **FAIL** - Return to understanding |
| Generic pattern applied without fit check | **FAIL** - Evaluate fit |

### When Gate Fails

```
Solution was forced, not emerged.

Action:
1. Set aside the current solution
2. Return to the problem
3. Understand more deeply
4. Let new solution emerge from understanding
```

## Gate 3: Fit Gate

### Core Question
**Does this solution fit the context naturally?**

### Gate Criteria

```markdown
## Fit Gate Checklist

- [ ] Addresses actual need (not assumed need)
- [ ] Works WITH existing constraints
- [ ] Natural for this context
- [ ] Would feel right to someone who knows the context

**Fit Status**: [Natural Fit / Partial Fit / Forced Fit / Misfit]
```

### Fit Indicators

| Natural Fit | Forced Fit |
|-------------|------------|
| Works with constraints | Fights constraints |
| Addresses actual need | Addresses assumed need |
| Feels natural in context | Creates friction |
| Minimal adaptation needed | Requires forcing |

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Fits context naturally | **PASS** |
| Works with constraints harmoniously | **PASS** |
| Creates friction with context | **FAIL** - Doesn't fit |
| Addresses wrong need | **FAIL** - Misunderstood |

### When Gate Fails

```
Solution doesn't fit the context.

Action:
1. Identify where friction occurs
2. Understand the context better
3. What constraints were missed?
4. What is the actual need?
5. Redesign to fit naturally
```

## Gate 4: Elegance Gate

### Core Question
**Is there anything extra? Is there anything missing?**

### Gate Criteria

```markdown
## Elegance Gate Checklist

- [ ] Nothing can be removed without loss
- [ ] Nothing is missing that's needed
- [ ] Every element serves the purpose
- [ ] Complexity matches problem complexity

**Elegance Status**: [Elegant / Cluttered / Incomplete / Both]
```

### Elegance Test

| Test | Beautiful Answer |
|------|------------------|
| Can anything be removed? | No—all serves purpose |
| Is anything missing? | No—all needed is present |
| Does every part earn its place? | Yes |
| Is complexity justified? | Yes—matches problem |

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Nothing extra, nothing missing | **PASS** |
| Every element earns its place | **PASS** |
| Superfluous elements present | **FAIL** - Prune excess |
| Necessary elements missing | **FAIL** - Complete |

### When Gate Fails

```
Too much or too little.

For excess:
1. Identify what doesn't serve purpose
2. Remove without loss
3. Verify solution still complete

For gaps:
1. Identify what's missing
2. Add what's needed
3. Verify not over-completing
```

## Gate 5: Coherence Gate

### Core Question
**Does this hang together as a unified whole?**

### Gate Criteria

```markdown
## Coherence Gate Checklist

- [ ] Parts relate to each other naturally
- [ ] Consistent principles throughout
- [ ] Changes in one part make sense with whole
- [ ] Unified solution, not assembled pieces

**Coherence Status**: [Unified / Partially Coherent / Fragmented]
```

### Coherence Indicators

| Unified (Beautiful) | Fragmented (Ugly) |
|--------------------|-------------------|
| Parts connect naturally | Parts disconnect |
| Consistent principles | Inconsistent rules |
| Whole greater than parts | Just parts together |
| Seamless | Visible seams |

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Hangs together as unified whole | **PASS** |
| Consistent principles | **PASS** |
| Fragmented patchwork | **FAIL** - Unify |
| Inconsistent principles | **FAIL** - Align |

### When Gate Fails

```
Solution is fragmented, not unified.

Action:
1. What's the unifying principle?
2. How do parts actually relate?
3. Redesign with coherence
4. Ensure consistent principles
```

## Gate 6: Clarity Gate

### Core Question
**Can others understand this?**

### Gate Criteria

```markdown
## Clarity Gate Checklist

- [ ] Can be explained simply (without losing accuracy)
- [ ] Structure is visible
- [ ] Intent is apparent
- [ ] Others can understand why it's this way

**Clarity Status**: [Clear / Partially Clear / Obscure]
```

### Clarity Indicators

| Clear (Beautiful) | Obscure (Ugly) |
|-------------------|----------------|
| Explainable simply | Requires extensive setup |
| Structure visible | Structure hidden |
| Intent apparent | Intent mysterious |
| Others understand | Only creator understands |

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Can be explained simply | **PASS** |
| Structure and intent visible | **PASS** |
| Unnecessarily obscure | **FAIL** - Clarify |
| Requires creator to interpret | **FAIL** - Make transparent |

### When Gate Fails

```
Solution is obscure.

Action:
1. Can you explain it in 2 minutes?
2. What would make structure visible?
3. How can intent be made apparent?
4. Redesign for clarity
```

### Core Question

### Gate Criteria

## Appropriateness Gate Checklist

- [ ] Complexity matches problem complexity
- [ ] Investment matches value
- [ ] Scope matches need

**Appropriateness Status**: [Right-sized / Over-built / Under-built]

| Right-sized (Beautiful) | Over-built (Ugly) | Under-built (Ugly) |
|------------------------|-------------------|-------------------|

| Investment matches value | Over-invested | Under-invested |
| Scope matches need | Scope exceeds need | Scope below need |

### Pass/Fail

| Condition | Result |
|-----------|--------|
| Right-sized for purpose | **PASS** |
| Complexity matches need | **PASS** |
| Over-engineered | **FAIL** - Simplify |
| Under-built | **FAIL** - Complete |

### When Gate Fails

```
Wrong size for purpose.

For over-built:
1. What can be simplified?
2. What's beyond actual need?
3. Right-size to real requirement

For under-built:
1. What's missing?
2. What does the need actually require?
3. Complete to appropriate level
```

Right response to gate failure:
  Gate fails → Identify understanding gap → Understand deeper → Beauty emerges

## Claude-Specific Enhancement: Conformance Gate

> **Principle**: Claude follows patterns but lacks aesthetic sense. Conformance Gate enforces pattern matching.
> New code must demonstrably match existing codebase patterns.

### Core Question
**Does this new code match the patterns in this codebase?**

### Why This Gate Exists

Claude:
- Can generate correct but stylistically inconsistent code
- May apply generic patterns instead of codebase-specific ones
- Lacks intuitive sense of "how things are done here"
- Benefits from explicit pattern comparison

Conformance Gate ensures **pattern match before create**.

### Gate Criteria

```markdown
## Conformance Gate Checklist

Before writing new code:

- [ ] Found similar code in codebase (Grep)
- [ ] Extracted the pattern used
- [ ] New code follows same naming conventions
- [ ] New code follows same structural patterns
- [ ] New code follows same error handling approach
- [ ] Can cite similar code as pattern source

**Conformance Status**: [Conforms / Deviates / No Pattern Found]
```

### Conformance Heuristics

```markdown
## Pattern Match Checklist

Claude CAN verify these objectively:

□ Same naming convention?
  - camelCase vs snake_case vs PascalCase
  - Prefix/suffix patterns (e.g., I- for interfaces)

□ Same file organization?
  - Where similar files are placed
  - How files are named

□ Same structural patterns?
  - Class vs function vs module
  - Export style (default vs named)

□ Same error handling?
  - try/catch vs Result type vs callbacks
  - Error message format

□ Same import structure?
  - Relative vs absolute
  - Barrel exports vs direct imports

□ Roughly same complexity level?
  - Simple functions stay simple
  - Complex patterns where complexity exists
```

### Pattern Extraction Protocol

```markdown
## Find-Extract-Follow Protocol

BEFORE writing new code:

1. **FIND SIMILAR**
   └─ Grep: "class.*Service", "function.*Handler", etc.
   └─ Document: [similar code at file:line]

2. **EXTRACT PATTERN**
   └─ What naming convention?
   └─ What structure?
   └─ What error handling?
   └─ Document: [extracted pattern]

3. **FOLLOW PATTERN**
   └─ New code matches extracted pattern
   └─ Document: "Following pattern from [file:line]"

4. **CONTRAST CHECK**
   └─ Compare new code to existing
   └─ Verify visual/structural similarity
```

### Pass/Fail

| Condition | Result |
|-----------|--------|
| New code matches existing patterns | **PASS** |
| Can cite pattern source | **PASS** |
| Deviates without justification | **FAIL** - Align with patterns |
| No similar code searched | **FAIL** - Search first |
| Generic pattern, not codebase pattern | **FAIL** - Find local patterns |

### When Gate Fails

```
New code doesn't match codebase patterns.

Action:
1. SEARCH for similar code: Grep("similar pattern")
2. EXTRACT the pattern used
3. ALIGN new code with pattern
4. CITE the pattern source

Never: Write code that "looks right" generically
Always: Write code that matches what exists here
```

### Deviation Protocol

```
Sometimes deviation is correct. When deviating:

1. DOCUMENT why existing pattern doesn't fit
2. JUSTIFY the deviation
3. CONSIDER if pattern should change globally
4. MAKE deviation explicit, not silent
```

### Examples

**Bad (No Conformance Check)**:
```typescript
// New code written without checking patterns
export default class RateLimiter {
  constructor(private limit: number) {}
  check(req: Request): boolean { ... }
}
```

**Good (With Conformance)**:
```typescript
// Pattern source: src/middleware/auth.ts:12-30
// - Uses function export (not class)
// - Follows (req, res, next) signature
// - Uses async/await pattern

export const rateLimiter = (options: RateLimitOptions) => {
  return async (req: Request, res: Response, next: NextFunction) => {
    // Following auth.ts pattern...
  };
};
```

### Pattern Categories

| Category | What to Check | Where to Look |
|----------|---------------|---------------|
| **Services** | Class vs factory, naming | `src/services/*.ts` |
| **Middleware** | Signature, export style | `src/middleware/*.ts` |
| **Components** | Props pattern, hooks usage | `src/components/**/*.tsx` |
| **Utilities** | Function style, error handling | `src/utils/*.ts` |
| **Tests** | Describe/it pattern, mocking | `**/*.test.ts` |
